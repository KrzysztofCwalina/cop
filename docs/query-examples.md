# Ten captured provider queries: source-shaped Cop and JSON

These are actual request bodies received by a Python process provider through the
production `ProcessObjectProvider` and Python SDK. They are not invented JSON examples.
The probes adapt patterns from `DeferredProviderExecutionTests` and
`ProviderQueryRegressionTests`; nested Boolean combinations extend those patterns.
The existing 43 lazy-query tests and 7 core query regressions were also rerun successfully.

For every probe, the actual production `[query-cop]` output was independently parsed
and executed, producing structurally identical complete JSON requests. The Cop query
sections below are generated by the implementation, not handwritten equivalents.
Colon chains, lambda parameter names, and required named predicate definitions are
retained. `Items` is the schema collection name after resolving the `items` alias.

`items` and `others` are deferred `Items` collections bound by the harness to the
primary and secondary target directories. Each directory contains this real JSON input:

```json
[
  { "Name": "AlphaClient", "Active": true, "Size": 12 },
  { "Name": "BetaClient", "Active": false, "Size": 20 },
  { "Name": "AlphaService", "Active": true, "Size": 5 }
]
```

The Python provider deliberately returns all three input records and ignores filters.
This checks host residual correctness and request delivery, not provider-side scan
performance. Existing language/format provider tests separately check provider pruning.

All nonterminal pipelines generated **zero query requests while composing**. After
enumeration, each used one request except the two-target concatenation, which used two.
Repeated enumeration and a second execution of each command generated **zero extra requests**.
The count terminal executes immediately when invoked, not when its declaration is parsed.

## Reading the examples

The Cop fences use harness-supplied collection bindings, not standalone CLI programs.
Case 1 has a local count terminal; case 9 has an additional local predicate. Their
generated provider programs intentionally omit those host-only operations.

JSON below is complete, including both `filter` and `collectionFilters` when sent.
Only indentation and local target-path redaction have been applied:
`<primary target>` and `<secondary target>` replace the absolute local paths.
Unmodified received JSON bodies are preserved as per-case `original/wire.jsonl`
and `equivalent/wire.jsonl` session artifacts alongside the runnable capture harness.
All operation codes shown are captured values, not illustrative substitutions.

## 1. Unfiltered query with a local count terminal

Test pattern: `QueryableTerminals_ReturnExactValues`.

### Cop evaluated by the interpreter

```cop skip

```

### Actual generated Cop for each provider query


Host-only stages (diagnostic output; not sent to providers):

```text
[query-local] probe.Items root=<primary target>: Count executes locally
Items.Count
```

Count triggers execution, but there is no aggregate in the provider request. The provider-equivalent expression returns the three records; the original program counts them locally.

Original result: `3`. Provider-equivalent replay result: `AlphaClient, BetaClient, AlphaService`.

## What the captures demonstrate

- Predicate names and source-file boundaries disappear into JSON filter trees, but
  names and required predicate definitions remain in the generated Cop source.
- Boolean grouping, negation, numeric comparisons, and exact string equality survive transport.
- An untranslatable local stage is not silently advertised as provider pushdown.
- Count and concatenation are not aggregate/union operations in the provider protocol.
- JSON currently repeats the normalized filter under `filter` and `collectionFilters.Items`.
- Producing readable Cop text need not require changing the wire protocol.

See [Provider query representation](query-language.md) for node kinds and operation codes.
